# Version 1.1.6

**Release Date:** August 31, 2026

## Overview

Version 1.1.6 separates the channel-neutral bridge core from WeChat-specific code, adapts Codex thread tracking to upstream behavior introduced after Codex CLI `0.149.1`, and preserves replies when WeChat context tokens become unavailable. It also changes emoji binding ownership, lowers the Node.js floor to `22.13.0`, and documents the complete Linux npm lifecycle-script approval workflow.

## Bridge Core and WeChat Channel Separation

The new `src/core` layer contains channel-neutral conversation and attachment types, the `BridgeChannelPort` interface, control-command parsing, inbound message routing, event forwarding, and shared text utilities. `src/channels/wechat` contains WeChat message conversion, final-reply formatting, transport-facing event handling, `WechatChannelPort`, and the pending outbound queue. WeChat context tokens are carried as opaque channel state and are not interpreted by the core.

Direct bridge and daemon runtimes now use the same canonical grammar for `/status`, `/resume`, `/new`, `/stop`, `/reset`, `/confirm`, `/deny`, and `/answer`, followed by the same routing order: authorization, control command, pending approval, pending structured input, deferred input, busy state, and task dispatch. Daemon emoji bindings remain a separate layer before the core router. Both runtimes use the same event-forwarding contract for output, final replies, approvals, user-input requests, mirrored input, session or thread switches, completion, failure, and shutdown. Published CLI command names, state-file locations, message formats, and adapter interfaces remain unchanged. Compatibility exports preserve existing `src/bridge` import paths, while Fake Channel tests verify the core without adding a second production channel.

## Codex Upstream Compatibility

### Upstream behavior change

Codex `rust-v0.149.1` does not contain automatic TUI thread-title generation. Upstream change `#40492`, **Generate descriptive TUI thread titles**, added the feature to later releases. The title generator starts a hidden helper thread with `ephemeral: true` and `threadSource: feature(system)`. The app-server `thread/started` notification contains full thread metadata, but `thread/status/changed` contains only `threadId` and `status`.

The previous bridge followed every idle thread whose cwd matched the active workspace. With the upstream title helper present, the hidden thread could replace the shared thread ID before a later root-thread status switched it back. Runtime logs showed repeated thread-switch notices, interruption of a WeChat-owned task, and missing local-input mirroring after the bridge followed the helper thread.

### Thread validation and resume

Version 1.1.6 resolves unknown status IDs with `thread/read`. Local following now requires an exact ID in the current cwd, no parent thread, and `ephemeral !== true`; `thread/started` and startup restore use the same root-thread conditions. The bridge records the installed Codex version at startup. Codex CLI `0.149.1` and `0.151.0` are validated, while later versions remain launchable and are logged outside the validated range.

WeChat `/resume` now completes target validation, app-server `thread/resume`, visible-client switching, and shared-thread commit in that order. A failed visible switch retains the previous thread. Bridge-owned resume replay notifications are suppressed during a five-second settling period and cleared by a real local turn. Headless local thread changes trigger immediate deduplicated subscription, so local prompts continue to emit `mirrored_user_input` before their final replies.

After a WeChat-owned turn completes, weak `thread/status/changed`, `thread/started`, and session-fallback signals are ignored for 150 milliseconds. A real local `turn/started` or user-message event clears that block immediately.

Local Codex thread notices are suppressed only during the first 500 milliseconds after a final reply. A later local `/resume` switch is forwarded to WeChat and clears the five-minute numbered resume snapshot. This replaces the earlier broad suppression that could hide real local thread changes.

### Event ordering and diagnostics

Direct bridge and daemon event handlers use one Promise chain per runtime. Thread, status, final-reply, and lifecycle events are processed in arrival order. A failed handler records `event_forward_failed` and does not stop later events. Codex fatal diagnostics retain the last six non-empty app-server log lines within a 500-character limit, while the WeChat-facing fatal message omits the internal app-server tail.

## WeChat Reply Recovery

When `sendmessage ret=-2` marks the recipient context as stale, or no cached context token is available, direct bridge and daemon runtimes store the unsent text in `~/.cli-bridge/workspaces/<workspace-key>/pending-wechat-messages.json`. The file is loaded after restart. The next inbound WeChat message refreshes the recipient context and triggers ordered delivery; each entry is removed only after a successful send.

WeChat send diagnostics now record `wechat_send_started`, `wechat_send_completed`, and `wechat_send_timeout` with context, recipient, attempt, and elapsed time. These records distinguish model-output delays, WeChat transport delays, retries, and stale-context recovery.

## Behavior Change: Standalone Emoji Bindings

Standalone bridges previously loaded the daemon emoji-binding store, rewrote messages that started with a bound emoji, and intercepted `/bind`, `/unbind`, and `/bindings`. That behavior was incorrect for a bridge connected to one fixed adapter: emoji and binding-like text could be consumed before reaching the selected CLI.

Version 1.1.6 removes emoji binding resolution and management from standalone bridges. Standalone input is forwarded to the selected CLI unchanged. `wechat-daemon` retains emoji command resolution, adapter switching, `/bind`, `/unbind`, `/bindings`, and the existing binding data. Users who require WeChat emoji bindings should run the daemon workflow.

This removes the standalone emoji-binding workflow introduced in 1.1.0. The daemon emoji-binding workflow and stored bindings are unchanged.

## Installation and Upgrade

The Node.js minimum is `22.13.0`, checked as a complete major, minor, and patch version. Node.js `22.12.x` is rejected; `22.13.x`, 23, and 24 are accepted. `CLI_BRIDGE_SKIP_NODE_CHECK=1` bypasses the launcher check. CI runs Node.js `22.13.0` and Node.js 24 on Ubuntu, macOS, and Windows. OpenCode support remains `>=1.18.0 <2.0.0`.

Newer npm versions on Linux can complete installation while blocking the `cli-wechat-bridge` postinstall and `node-pty` install scripts. In that state, PTY-dependent paths can fail and the macOS/Linux `spawn-helper` permission repair does not run. A clean installation is:

```bash
npm uninstall -g cli-wechat-bridge
npm install -g cli-wechat-bridge@latest --allow-scripts=cli-wechat-bridge,node-pty
```

Persistent user-level approval is:

```bash
npm config set allow-scripts=cli-wechat-bridge,node-pty --location=user
npm install -g cli-wechat-bridge@latest
```

The package name must remain in the install command. Running only `npm install -g --allow-scripts=...` makes npm read the current directory as a package and can produce `ENOENT /home/<user>/package.json`. After installation, run `wechat-daemon --doctor` and confirm that `node-pty` is loaded.

Primary-package upgrade:

```bash
npm install -g cli-wechat-bridge@latest
```

Existing scoped-package users can upgrade with:

```bash
npm install -g @unlinearity/cli-wechat-bridge@latest
```

No runtime data migration is required. Restart running daemon, bridge, and visible CLI processes after upgrading.

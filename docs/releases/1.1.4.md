# Version 1.1.4

**Release Date:** August 23, 2026

## Overview

Version 1.1.4 consolidates startup into four commands — `wechat-codex`, `wechat-claude`, `wechat-opencode`, and `wechat-pi`: one command handles the WeChat login check, daemon delegation, and local bridge provisioning, replacing the separate family of bridge commands. It also lands the fixes from a full logic audit of the codebase — more than twenty concurrency and stability defects, including one that had left several safety mechanisms inoperative on Windows since the first release. On the OpenCode side, two missing abilities arrive: agent questions can be answered directly from WeChat, and `/resume` restores earlier sessions.

## Startup

The four direct commands are complete entry points. Running one validates the WeChat login first, delegates to a same-directory daemon when one is running, and otherwise starts a local bridge that stops when its terminal closes. The separate `wechat-bridge*` commands are removed; their role is folded into these four. The `wechat-*-start` commands keep working and will be removed in 1.1.5. The WeChat welcome a standalone bridge sends is trimmed to two lines; the daemon keeps its full command and emoji reference.

## Stability

Process decisions now verify identity before acting. Checks previously trusted a recorded pid alone: when the OS reassigned a departed bridge's pid to an unrelated program, a new bridge could refuse to start over a lock conflict pointing at that unrelated process, and the cleanup path carried a real risk of terminating it. Lock reclamation, orphan cleanup, and parent watching now compare the process command line before acting. A more fundamental Windows defect was fixed alongside: the process-scan PowerShell statements were joined without a separator, so every scan had failed to parse and returned empty since the first release, leaving peer detection, orphan reaping, and daemon identity checks inoperative on that platform.

The daemon is consistent under concurrency. WeChat messages, IPC requests, and startup could previously demand the same adapter simultaneously, producing duplicate terminals, doubled replies, and state files overwriting each other; same-adapter requests now run sequentially. The input-waiting path is corrected as well: after an agent issues a choice or form request, a reply arriving too quickly used to bypass the registration and be typed into the terminal as plain text — the request is now registered the moment it arrives, so fast replies match correctly. `--session-start-mode new` finally works for codex: the flag was either ignored or forwarded as an unknown argument that made the client refuse to start. A daemon that fails no longer strands child processes, a crashed adapter is rebuilt by the next switch command, and `/answer` locates the session actually awaiting a reply across slots, as `/confirm` and `/deny` already did.

Delegation to the daemon now respects real timing. A cold start almost always hit the two-second timeout and exited, while the daemon kept processing and opened the terminal moments later — the user saw a failure for what was in fact a successful start. The deadline is now 45 seconds, and a daemon confirmed unreachable or failing causes the launcher to fall back to starting a local bridge rather than aborting.

Each adapter recovers from its own failure modes. OpenCode streaming no longer drops content (repeated words and table separators were mistaken for replays and discarded); Pi recovers from a dropped extension connection instead of remaining busy indefinitely and reports unexpected exits as fatal errors; Codex resubscribes to the shared thread immediately after an unexpected reconnect so pending approvals remain answerable; two Claude bridges in one directory no longer overwrite each other's approval wiring. `/stop` cleanly clears a Claude approval in progress, and an interrupted Codex turn no longer yields a duplicate reply moments later.

Shared state and network requests carry complete timeout coverage. The state files shared between bridge and terminal are written atomically, so an interrupted write no longer reads on the other side as a missing bridge; WeChat API calls are bounded from connection through full response-body read and no longer hang on a stalled server. A message arriving while the terminal is still starting waits for readiness instead of erroring with "not ready", and a long reply interrupted mid-delivery reports how many parts went unsent.

## OpenCode

Agent questions can now be answered from WeChat: when an OpenCode agent requests input through its question feature, `/answer` replies are delivered end to end — previously there was no way to respond from the phone. Every spawned opencode server receives a one-time random password; the SDK client and health probes send the matching credentials, so other local processes can no longer connect and drive the server. The retry status is treated as busy, the dual event streams deduplicate by server frame id, and directory matching works on POSIX hosts. WeChat `/resume` lists the recent sessions for the current directory and restores the selected one, syncing the visible terminal.

## Attachments and Install

Auto-sent attachments now cover ordinary files an agent mentions in a reply — source, documents, archives — while executables and installers (`.exe`, `.dll`, `.bat`, `.ps1`, `.sh`, and similar) are excluded from automatic upload. The mirror package `@unlinearity/cli-wechat-bridge` ships its install script again, restoring working PTY adapters on macOS and Linux installs.

## Upgrade Notes

Upgrade the primary package with:

```bash
npm install -g cli-wechat-bridge@latest
```

Existing scoped-package users can continue with:

```bash
npm install -g @unlinearity/cli-wechat-bridge@latest
```

After upgrading, restart every running bridge, daemon, and terminal. Replace any `wechat-bridge*` command still present in scripts or shell history with the corresponding direct command; the deprecated `wechat-*-start` aliases keep working in this release and go away in 1.1.5.

## Compatibility

Node.js `>=24.0.0` remains required. OpenCode `>=1.18.0 <2.0.0` is supported, verified against 1.18.18 and 1.18.21. Old `claude-runtime/` directories are superseded by per-instance ones and can be deleted manually; no data migration is needed.

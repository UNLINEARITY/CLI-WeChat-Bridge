# Version 1.2.2

**Release Date:** October 12, 2026

## Overview

Version 1.2.2 expands interaction between WeChat, WeCom, and local CLIs with live language switching, remote answers to Claude Code questions, and ordered approvals. It also fixes subagent events interfering with parent tasks in OpenCode and Codex, incorrect OpenCode 2 form answers, and missing Pi errors and interruption status.

## New Features

### Switch Bridge Messages with `/lang`

Direct-launch and daemon modes support these commands on WeChat and WeCom. The local test channel uses the same command grammar:

| Command | Effect |
| --- | --- |
| `/lang` | Show the current language and switching instructions |
| `/lang zh` | Switch to Chinese |
| `/lang en` | Switch to English |

- `/language` is an alias. Language arguments also accept `chinese`, `english`, `中文`, and `英文`. Invalid arguments return usage instructions rather than becoming model prompts.
- Changes take effect immediately, and the daemon updates bridge messages in all connected companions; CLIs started later inherit the current language. Language switching works without an active CLI and while a task is running or awaiting approval or answers.
- Preferences are saved to `language.json` in the active data directory, normally `~/.cli-bridge/language.json`. Startup precedence is: valid `CLI_BRIDGE_LANG` > saved preference > Chinese. Other independently running bridge processes read the saved value on their next startup.
- Model and plan controls, approvals, question guidance, session switching, status reports, and busy or input-wait messages now have Chinese and English text. This setting controls bridge messages; model replies, original questions and options, native CLI interfaces, and upstream errors retain their original content.

### Answer Claude Code Questions Remotely

Claude Code `AskUserQuestion` can now be answered from WeChat or WeCom, with single selections, multiple selections, custom answers, option descriptions, and text previews.

For a single question, use `/answer 1` to select an option or `/answer <text>` to provide a custom answer. Answer all questions in a multi-question request together, for example:

```text
/answer 1=Yes;2=2;3=1,2;4=Custom layout
```

Question numbers identify the questions; option numbers or original labels identify the selections, with commas separating multiple choices. Answers are returned through Claude hooks while preserving the original questions and tool input. Generic automatic approval no longer lets `AskUserQuestion` proceed without answers.

Consecutive requests are presented in order. Local completion, `/stop`, `/reset`, and session end clear the corresponding requests. Hook timeout or disconnection removes the remote question and instructs the user to answer in the local Claude terminal or interrupt with `/stop`. Failed answer writes remain available for retry. Once a request expires, late write results cannot restore its state or overwrite newer questions.

### Local Test Channel and E2E Runner

The new `local` channel receives inbound messages through a JSONL inbox and records outbound messages in a transcript. Messages follow the daemon's command, dispatch, and reply paths without requiring WeChat login or WeCom Bot credentials.

The repository adds `npm run e2e`, which runs a real CLI through a PTY host and provides a read-only terminal mirror for inspecting its TUI. Scenarios cover:

- Remote prompts and final replies.
- Mirrored local terminal input and its replies.
- `/resume` listings and an actual switch to a different session.
- Remote and local terminal input after restoring a session.
- `/model` selection and entering and leaving `/plan` mode.

The runner supports scenario selection, retained diagnostic output, and disabling the terminal mirror. The complete scenario sequence currently focuses on Claude Code. It makes real model calls and requires a working CLI installation and model access configuration; run it in a test environment with everyday bridge and daemon processes stopped.

## Improvements

### Ordered Approvals Stay in Sync with the Local Terminal

Codex, Claude Code, and OpenCode keep pending approvals in order. In daemon mode, `/confirm` and `/deny` now handle one displayed request at a time instead of resolving the queue in a batch, then present the next request. Direct-launch mode uses the same behavior.

- Approvals accepted or rejected in the local terminal are removed from the remote pending list.
- Approvals are checked against their request IDs. Duplicate notifications and late events cannot restore completed requests, and expired approval requests cannot be submitted again.
- Failed submissions retain the current request for retry, and concurrent confirmations do not write the same decision twice.
- Codex and OpenCode route permission requests from owned subagents, including nested subagents, through the parent task while preserving its reply destination.

### Subagent Events Preserve the Parent Task

- **OpenCode:** A subagent creating a session, updating its status, or producing output is no longer mistaken for a user changing sessions in the TUI. This prevents parent-task interruption, missing replies, and input being sent to the wrong session. Explicit TUI session selection and local new-session requests are still followed.
- **Codex:** When following local sessions from events, subagent and ephemeral threads are identified so subsequent status or turn events carrying only a thread ID cannot automatically replace the parent task or trigger an incorrect session switch.

### CLI Compatibility and Automated Checks

- The validated Codex range expands from `0.149.x`–`0.157.x` to `0.149.x`–`0.161.x`.
- Weekly compatibility checks continue to cover OpenCode 1.18 and OpenCode 2 and explicitly allow required upstream CLI installation scripts.
- Codex checks validate the schema fields used by the bridge and `--remote`; Claude Code checks cover `--settings` and `--resume`; Pi checks load the bridge extension and verify session state and model-list IPC.
- OpenCode HTTP health probes validate response content, apply a three-second timeout to each request and body read, and use a thirty-second overall health-check window so startup races cannot leave the check hanging.

Capability checks do not call models. They verify interfaces and runtime capabilities rather than a complete conversation.

## Bug Fixes

- **OpenCode 2 form answers:** Single and multiple selections map the displayed `label` to the actual `value`, fixing incorrect submissions when the two differ. Custom text and boolean/integer form fields remain supported.
- **Pi error reporting:** Provider failures are forwarded to the bridge even when no reply text was generated, preventing the task from ending silently.
- **Pi interruption status:** Preserve `agent_settled.aborted`, report interrupted results correctly, retain partial replies, and clear the active task so the next request can run. Older events without the flag remain supported.
- **Claude Code native controls:** Automatic context chips and suggestion placeholders no longer count as an input draft, fixing remote `/model` and `/plan` on newly started sessions. Actual unsent drafts still block remote controls.
- **Claude Code permission notifications:** Previously auto-approved commands are no longer reused to construct a new approval prompt. Local permission dialogs without a remote approval hook direct the user to the terminal.
- **Message interpolation:** Dollar signs and placeholder-like text such as `{name}` in parameters are preserved literally, preventing unintended substitutions in model names, paths, or message content.
- **Chinese messages and queued retries:** The deferred Codex queue recognizes busy, pending-approval, and local-input-wait errors in Chinese and retains the corresponding requests for retry.
- **Source startup and Node.js 22.13:** Replace TypeScript syntax in the WeChat driver that Node strip-types cannot load, restoring source-mode daemon startup. Claude hook subprocess tests explicitly enable `--experimental-strip-types`, fixing CI failures on Node 22.13.0.
- **README presentation:** Add the AtomGit mirror link and fix typing SVG parameters and badge layout across hosting platforms.

## Upgrade and Compatibility Notes

### Install and Restart

The minimum Node.js version remains `22.13.0`; Pi requires `22.19.0` or newer. Existing data needs no migration, and existing launcher commands remain available.

Upgrade the primary package:

```bash
npm install -g cli-wechat-bridge@1.2.2
```

Users of the existing scoped package can continue upgrading it:

```bash
npm install -g @unlinearity/cli-wechat-bridge@1.2.2
```

Restart running bridge, daemon, and visible CLI processes after upgrading to load the new hooks, approval request identifiers, and language synchronization. Older companions can still display state but must restart before remote approvals work; companions that cannot update their language live return a restart notice. Once the new version is running, subsequent `/lang` changes require no restart.

See [language configuration](../configuration.md#界面语言) for saved preferences and startup environment variables.

### Permission Defaults and Scope

The bridge's Claude Code startup settings add `WebFetch(domain:*)` by default. Set `CLI_BRIDGE_STRICT_APPROVAL=1` to omit that rule and disable bridge automatic approvals for Codex and Claude; existing deny rules and sandbox restrictions still apply.

Claude sandbox network dialogs that do not trigger a `PermissionRequest` hook still require action in the local terminal. Pi has no added bridge tool-approval layer: its `--approve` flag trusts project configuration, extensions, and local files rather than enabling per-tool approval.

- **Quality:** `npm run quality` passes lint, strict source type checking, all 813 tests on Node 24, and the build. The complete 813-test suite also passes on Node 22.13.0.
- **Dependencies and packaging:** Frozen-lockfile installation passes. The npm package contains 101 files, including 14 executable command entrypoints, `dist/`, `README.md`, and `LICENSE.txt`; it excludes source, tests, runtime state, logs, and `node_modules/`.

Validation covers automated regressions, real CLI interface probes, and local message transport. Live WeChat and WeCom delivery, and complete conversations with real models for each adapter, still require separate acceptance testing.
